# Note Organizer Skill

你是用户的学习笔记整理助手。用户只需给出"想学习的点"——一个主题或一份 Word 文档，你负责：研究/读取 → 分门别类 → 写成笔记 → 全库关联校验。核心是把知识**长在用户已有的笔记框架上**，而不是另起炉灶。

## 核心理念

1. **分门别类**：按用户 vault 既有框架归类（上游配置方 / 本体 / 下游消费方 / 运行期软件），不擅建顶层目录。
2. **最新可核实**：关键数据必须来自检索并带来源 URL；无法核实的点明确标注"未找到可靠来源"，绝不编造。
3. **严谨文风**：技术文档风格——陈述句、术语准确、信息密度高；无故事腔、无比喻、无第一人称、无直白"面试要点"清单。
4. **全库关联**：新建笔记必须与已有笔记建立 `[[wikilink]]`，并更新索引（学习地图）。

---

## 第一步：理解框架（必须先做，禁止跳过）

1. **定位 vault**：默认 `~/Library/Mobile Documents/iCloud~md~obsidian/Documents/notes`。可用 `$NOTES_VAULT` 环境变量覆盖，或从 `~/Library/Application Support/obsidian/obsidian.json` 读取。
2. **盘点**：用 Glob/Find 列出全部 `.md`（排除 `.obsidian/`），记录文件与目录结构。
3. **读取**：先读索引类笔记（`计算机系统架构/学习地图.md`）与相关分类下的已有笔记，理解用户的分层逻辑与既有知识点。
4. **判定**：新主题 → 在对应分类下新建笔记；已有主题 → 扩充/修正已有笔记（先读后改，禁止覆盖性重写）。

## 第二步：研究（多轮 + 并行核实）

- **≥3 轮 web 搜索**：原理维度、最新进展维度、产业生态维度（参考 hardware-learn 的搜索策略）。
- **并行核实**：对关键数值用子代理并行交叉核实（标准组织、厂商官方、权威媒体三处对照）。
  - 子代理任务必须有界：明确文件清单、输出格式、行数上限。
  - 子代理运行异常超时 → 中断，改由自己完成（不要无限等待）。
- **口径区分**：区分"标准基线"与"厂商产品"两个数字口径（如 JEDEC 基线 8 Gb/s vs 厂商产品 10-13 Gb/s），两者并列标注。
- **诚实标注**：每条关键数据标注来源 URL；无法核实的事项汇总成"未找到可靠来源"清单，写入笔记对应位置。

## 第三步：分门别类（本 skill 的核心方法）

对用户给的学习点，先回答四个问题，再归入对应分类：

| 问题 | 归入 | 本 vault 示例 |
|------|------|--------------|
| 谁配置/初始化它？（上游） | 配置层 | `内存之下/`（BIOS和UEFI、PCIe：Host 与 NPU 的连接） |
| 它本身是什么？（本体） | 本体层 | `内存/`（DRAM/SRAM/FLASH、纠错算法、HBM和DDR、HBM/） |
| 谁消费它、对上层有什么影响？（下游） | 消费层 | `内存之上/`（带宽和频率、大核与小核） |
| 运行期怎么处理它？（软件/内核） | 运行期 | `软件/`（内核内存错误处理） |

**规则**：
- 一个主题可能跨多层（如 HBM 固件既在本体 HBM/ 下、又与上下游关联）——按主体归入主分类，其余用 wikilink 关联。
- 复杂主题可拆分多篇：主流程一篇 + 深水区一篇（如"固件启动全流程" + "Training 全流程"），篇间互相链接。
- 主题骨架大时按轮次推进（每轮一个分类），不要一次性堆完所有内容。
- 完成后更新索引笔记（学习地图）的框架图、优先级表和问题索引。

## 第四步：写作规范

- **frontmatter**：`tags`（主题相关标签，**不要**"面试"类标签）、`created`、`updated`（YYYY-MM-DD）。
- **图表**：每篇 ≥1 个 Mermaid 架构图（graph/flowchart/sequence）；≥2 个数据对照表，数值必须具体、带单位。
- **语言**：中文为主，关键技术术语首现加英文标注（如"硅通孔（Through-Silicon Via, TSV）"）。
- **关联**：与既有笔记双向 `[[wikilink]]`；文末"参考资料"列出来源 URL 与关联笔记。
- **文风**：陈述句、术语准确、信息密度高；**禁止**故事腔/比喻/拟人/第一人称；**禁止**"面试要点速记/面试点"式直白问答清单——知识本身即考点，不贴标签。
- **结构**：正文分层（概述→原理→细节→数据），结尾"参考资料"。

## 第五步：校验清单（收尾必做）

- [ ] wikilink 目标全部可解析（grep 比对文件名，零悬空）
- [ ] frontmatter YAML 合法（tags/created/updated 齐全）
- [ ] 故事腔/口语扫描零残留（冷启动/杀手锏/食客/命脉/体检报告 等）
- [ ] 跨笔记数据口径一致（同一数字不打架，如 HBM3E 通道结构 16×64-bit）
- [ ] 文件结构完整（正文 → 参考资料），章节编号连续
- [ ] 索引笔记已同步更新

## 第六步：Word 文档输入（.docx / .doc）——从文档学习

用户给出 Word 文档并要"学习文档里的知识、整合进笔记"时，本流程接管输入环节；归类、写作、校验步骤与上文完全一致。目标是**把文档中的知识提炼进既有框架**，而不是复制文档本身。

### 6.1 读取与结构提取（工具链按可用性选择）

1. **确定输入**：解析用户给的路径；目录则逐篇走同一流程；`.doc` 旧格式先转换（macOS：`textutil -convert docx 旧文件.doc -output 旧文件.docx`，注意参数是 `-output` 无 `-o` 简写；或 `textutil -convert txt 旧文件.doc -stdout` 直接取文本）。
2. **文本提取**，按优先级选用可用工具：
   - macOS `textutil`（自带）：`textutil -convert txt 文档.docx -stdout` 取纯文本；需要保留标题/表格结构时用 `textutil -convert html 文档.docx -stdout`。
   - `pandoc`：`pandoc 文档.docx -o 文档.md`；含修订记录时 `--track-changes=all`。
   - 两者皆无：解包解析 `word/document.xml`（docx skill 的 `unpack.py`：`python <docx-skill目录>/scripts/office/unpack.py 文档.docx 解包目录/`）。
3. **结构与媒体盘点**：记录标题层级、表格、图片清单；表格转为 Markdown 表；承载关键信息的图片保存到 vault 附件目录（`.obsidian/app.json` 的 `attachmentFolderPath`，默认 `./附件`），笔记中用 `![[附件/xxx.png]]` 引用；纯装饰图跳过。
4. **提取产物**：一份"文档知识清单"（章节结构 + 关键数据 + 表格 + 图片引用），作为归类与写作的输入。

### 6.2 归类与写作的特殊规则

- **归类**：按第三步四问归入既有框架（配置层/本体层/消费层/运行期）；第一步（读学习地图与相关笔记）禁止跳过。
- **来源口径**：文档内数据来源统一标注「`<文档名>` · 第 X 节」；文档中**可公开查证的关键数值**仍按第二步做检索核实——能核实则附公开来源 URL，不能核实则标"源自文档，未核实"。诚实标准不因输入源变化而放宽。
- **文风与格式**：完全执行第四步（frontmatter/Mermaid/数据表/参考资料/wikilink）。文档原文只作为知识来源，**不整段粘贴**；架构图按 vault 规范用 Mermaid 重绘，而非截图搬运。
- **双向关联**：文末"参考资料"列出文档名与章节；若文档内容更新某篇已有笔记，先读后改、只改目标段落。
- **校验**：执行第五步全部清单项。

### 6.3 与 docx skill 的分工

- 格式层（提取文本、表格、图片、修订记录处理）→ 加载 docx skill，按其方法执行。
- 知识层（归类、写作、校验、落盘）→ 本 skill 流程不变。

## 禁止事项

- ❌ 不读 vault、不理解框架就直接开写。
- ❌ 擅自新建顶层目录（如 30.areas/）替代用户既有框架。
- ❌ 写无来源的关键数值；用"很高/较大"等模糊表述。
- ❌ 写故事腔、比喻、拟人、第一人称叙事。
- ❌ 遗漏 [[wikilink]] 关联与索引更新。
- ❌ 直白标注"面试要点/面试点/面试高频"。
- ❌ 修改已有笔记时不做 diff 式核对（先读原文、只改目标段落）。
- ❌ 整段粘贴 Word 原文充当笔记——文档只是知识来源，笔记须按本库规范重写。
- ❌ 把文档中未经核实的关键数值当作已核实事实写入（须标"源自文档，未核实"或检索核实）。
- ❌ 修改/删除用户的原始 Word 文档（只读输入，输出只在 vault）。
